# Feature Specification: 运行事件流

**Feature Branch**: `specs/007-run-event-stream`

**Created**: 2026-11-21

**Status**: Draft

**Input**: "流式输出借鉴 Streaming / AG-UI 笔记好好实现；后期要集成网页端（AG-UI、类似 Codex 的操作确认、工具结果、断点重连）。先做核心层的事件模型：截断修复、事件模型、CLI 流式，网页相关部分等网页出来再做。"

## 范围与边界

一轮对话从开始到结束会经历多次模型调用、工具执行、用户确认。本功能给每一轮定义一份**有序、有唯一终态的运行事件序列**，作为所有交互入口观察执行过程的唯一契约；并让 `AgentOS chat` 成为第一个消费方：实时显示回答文字、工具进度与终态，支持中途取消。

同时修正一个正确性问题：模型因输出上限被截断或被内容策略过滤时，本轮目前仍按成功结束，本功能改为非成功终态。

本功能只交付核心层契约与 CLI 消费方。以下内容属于后续"Web 流式接口"（随 US-5 会话 REST 一起做），本期**不做**：事件持久化与断线重放、SSE 订阅端点、AG-UI 翻译层、网页端操作确认接口、多实例事件通知、推理内容事件、工具参数逐段流式。本期的事件契约必须能被这些后续能力原样承接，不因接入网页而改动核心循环（宪章 1.1.0 原则 II：事件契约随 ReAct 循环交付，Web 流式接口随 US-5 交付）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 在 CLI 中实时看到执行过程 (Priority: P1)

用户在交互式 `AgentOS chat` 中提问。模型开始输出后，文字边生成边显示；Agent 调用工具时，终端显示"哪个工具开始了、结束了、结果如何、用了多久"；整轮结束后显示明确的结束状态。用户不再面对几十秒无响应的终端。

**Why this priority**: 当前 CLI 在整轮结束前没有任何输出，默认整轮上限 300 秒，长任务无法判断是在推理、在执行工具还是已经卡住。

**Independent Test**: 用可编排的桩模型依次返回"文字 + 工具调用"和"最终文字"，观察终端输出顺序与内容。

**Acceptance Scenarios**:

1. **Given** 交互式 chat，**When** 模型分多段输出回答，**Then** 每段到达后立即显示，整轮结束后不再重复打印完整回答。
2. **Given** 模型一次请求两个工具，**When** 工具依次执行，**Then** 每个工具各显示一行开始提示（工具名与脱敏、限长后的参数摘要）和一行结束提示（成功 / 失败 / 被拒绝 / 超时，及耗时），顺序与实际执行顺序一致。
3. **Given** 某个工具需要用户确认，**When** 确认提示出现，**Then** 它排在该工具的开始提示之后，用户作答后才出现该工具的结束提示；确认提示只出现一次。
4. **Given** 模型先输出一段说明再调用工具、之后给出最终回答，**When** 整轮成功，**Then** 中间说明与最终回答都按到达顺序显示，二者之间以工具进度行分隔。
5. **Given** 已显示部分文字后本轮失败或超时，**When** 终态到达，**Then** 终端标明本次回答未完成及失败原因，不把半截文字当作完整回答。
6. **Given** 非交互模式 `chat --message`，**When** 本轮成功，**Then** 标准输出只包含最终回答（与本功能之前一致），工具进度与状态行写到标准错误，便于脚本使用。

---

### User Story 2 - 截断或被过滤的回答不算成功 (Priority: P1)

模型因达到输出上限被截断、或因内容安全策略被过滤时，本轮以非成功状态结束，用户看到明确原因；这段不完整的回答不会作为成功历史进入后续轮次的上下文。

**Why this priority**: 这是正确性缺陷。半截回答被当作成功写库并参与下一轮推理，用户和后续轮次都会被误导；事件契约的终态码也依赖这一区分。

**Independent Test**: 桩模型分别返回"截断"和"被过滤"两种结束原因，在同步与流式两种调用方式下各运行一次。

**Acceptance Scenarios**:

1. **Given** 模型返回截断结束原因且没有工具调用，**When** 本轮收尾，**Then** 本轮为非成功状态，结束原因可区分为"输出被截断"，提示用户可调大输出上限或拆分任务。
2. **Given** 模型返回内容过滤结束原因，**When** 本轮收尾，**Then** 本轮为非成功状态，结束原因可区分为"内容被过滤"；系统不自动换模型或改写请求重试。
3. **Given** 上一轮因截断结束，**When** 同一会话发起下一轮，**Then** 上一轮只以"用户消息 + 未完成说明"进入上下文，截断文字不进入。
4. **Given** 截断发生在模型请求工具的那次响应里，**When** 本轮处理，**Then** 不执行这批可能不完整的工具调用，本轮以"输出被截断"结束。

---

### User Story 3 - 所有入口共用一份可信的事件契约 (Priority: P1)

后续的网页端、IDE 插件和当前的 CLI 都只依赖同一份运行事件契约，不读取模型供应商的响应结构，也不依赖某个入口的输出方式。契约保证：事件有序、可去重、终态唯一、内容已脱敏；后续接入事件存储、断线重放和 AG-UI 时，只需新增消费方。

**Why this priority**: 契约一旦被网页端依赖就很难再改。现在用 CLI 这个真实消费方验证它，比等网页出来再返工代价小。

**Independent Test**: 用记录型消费方运行成功、工具失败、确认被拒、超时、达到迭代上限、截断、取消等场景，逐条检查收到的事件序列。

**Acceptance Scenarios**:

1. **Given** 任意一轮，**When** 记录全部事件，**Then** 第一条是"轮次开始"，最后一条是唯一的终态事件（完成 / 失败 / 取消三类之一，失败带稳定错误码），终态之后不再有事件。
2. **Given** 任意一轮，**When** 检查序号，**Then** 序号在本轮内从 1 开始逐条加 1，没有重复和空洞，包括由不同执行线程产生的事件。
3. **Given** 模型的一次回答，**When** 文字分段到达，**Then** 事件依次为"消息开始 → 若干文字增量 → 消息结束"，三者带同一个消息标识；空文字片段不产生事件。
4. **Given** 一次工具调用，**When** 它被执行，**Then** 事件依次为"工具开始（含参数摘要）→ 工具结束（含状态、耗时、结果摘要）"，带模型给出的同一个工具调用标识；需要确认时，"确认请求"与"确认结果"位于这两条之间。
5. **Given** 一轮中的第 N 次模型调用，**When** 它开始与结束，**Then** 有对应的"步骤开始 / 步骤结束"事件，结束事件带结束原因与本次用量（服务端未返回时为空）。
6. **Given** 工具参数或结果里有密钥类内容，**When** 事件产生，**Then** 事件中的内容与模型看到的一样经过脱敏和限长，不含任何原始密钥。
7. **Given** 消费方处理事件时出错，**When** 本轮尚未结束，**Then** 本轮按现有"输出端失效"规则收尾，不会出现两个终态。

---

### User Story 4 - 中途取消当前轮次 (Priority: P2)

用户在交互式 chat 中发现 Agent 方向不对，按一次 Ctrl+C 取消当前轮次，而不是退出整个程序；本轮以"已取消"结束，之后可以继续输入下一条消息。

**Why this priority**: 长任务需要能及时止损；"取消"也是后续网页端停止按钮的同一能力。优先级低于前三项，因为现有整轮超时已能兜底。

**Independent Test**: 桩模型或桩工具人为延迟，在不同阶段（模型输出中、只读工具执行中、有副作用工具执行中、等待确认中）发出取消。

**Acceptance Scenarios**:

1. **Given** 模型正在输出，**When** 用户按 Ctrl+C，**Then** 输出停止，本轮以"已取消"结束，不再发起新的模型调用或工具调用，CLI 回到输入提示。
2. **Given** 只读工具正在执行，**When** 用户取消，**Then** 该工具被中止，结束状态记为中断，本轮以"已取消"结束。
3. **Given** 有副作用的工具正在执行，**When** 用户取消，**Then** 本轮以"已取消"结束，并明确提示"该操作可能已生效"，系统不自动重放或回滚。
4. **Given** 正在等待用户确认，**When** 用户取消，**Then** 该动作按未授权处理（零执行），本轮以"已取消"结束。
5. **Given** 没有正在执行的轮次，**When** 用户按 Ctrl+C，**Then** 行为与现在一致（退出 chat）。
6. **Given** 取消与本轮正常完成几乎同时发生，**When** 本轮收尾，**Then** 只有一个终态，以先被确认的那一个为准，界面与存储一致。

---

### Edge Cases

- 模型只返回用量信息、没有任何文字的分片，或只有角色信息的空分片：不产生文字事件。
- 一次回答只有工具调用、没有文字：不产生"消息开始 / 结束"。
- 流式输出过程中连接中断：已显示的文字保留，本轮失败，不换模型重新生成并拼接（沿用现有"交出首段文字后不重试"规则）。
- 首段文字之前发生暂时性错误并重试成功：用户只看到一份回答；重试本身以步骤内信息体现，不产生重复的消息事件。
- 达到模型调用上限、工具调用次数上限、整轮超时、租约丢失、进程关闭：各自映射到确定的终态与错误码。
- 工具结果被截断：结束事件标明已截断。
- 确认等待期间整轮计时暂停：事件时间戳如实反映等待时长，序号不受影响。
- 无人值守入口（`--message`、调试接口）：同样产生完整事件序列，只是不出现确认交互。
- 终端不支持控制字符或输出被重定向：CLI 退化为逐行输出，不输出光标控制序列。

## Requirements *(mandatory)*

### Functional Requirements

**事件契约**

- **FR-001**：每一轮产生一份运行事件序列。每条事件带：契约版本、会话标识、轮次标识、本轮内序号、事件类型、产生时间、类型相关的数据。序号由轮次在本进程内统一分配，从 1 开始连续递增；多个执行线程同时产生事件时也必须串行编号、按编号顺序交给消费方。
- **FR-002**：事件类型分三类。过程面：轮次开始、步骤开始 / 结束（一次模型调用为一个步骤）、工具开始 / 结束、确认请求 / 确认结果、提问请求 / 提问结果（`ask_user`）。数据面：消息开始、文字增量、消息结束。控制面：轮次完成、轮次失败、轮次取消。新增类型只能追加，消费方遇到不认识的类型必须忽略而不是报错。
- **FR-003**：每轮第一条事件是"轮次开始"，最后一条是且仅是一条控制面事件；控制面事件只在轮次结果持久化收尾之后发出，之后拒绝追加任何事件。
- **FR-004**：轮次失败事件带稳定错误码，至少区分：输出被截断、内容被过滤、整轮超时、达到模型调用上限、工具调用次数超限、模型服务不可用（按现有失败分类细分限流、认证、服务端错误、连接错误）、租约丢失、进程关闭中断、内部错误。错误码和面向用户的说明不含内部异常信息。
- **FR-005**：消息事件以消息标识关联开始、增量、结束；同一次模型调用的文字属于同一条消息。文字增量是非空文本，可以包含一个或多个字符；消费方不得假设一条增量对应一个 token。
- **FR-006**：工具事件以模型给出的工具调用标识关联；工具开始事件在该工具真正执行前、按单个工具发出，不等整批工具执行完。工具结束事件带状态（成功、失败、超时、被拒绝、被跳过、中断、结果未确认）、耗时、是否截断，以及与模型看到的同一份脱敏、限长后的结果摘要。
- **FR-007**：确认请求事件带确认请求标识、所属工具调用标识、动作类别和与 CLI 提示一致的脱敏摘要；确认结果事件带决定（允许一次、本会话允许、拒绝、超时、无人值守、取消）。提问事件同理。用户输入的拒绝原因与提问答案正文不进入事件。
- **FR-008**：步骤结束事件带本次模型调用的结束原因、请求模型与实际模型、输入输出 token 用量（服务端未返回时为空）；不带 prompt 和模型原始响应。
- **FR-009**：事件中的参数、结果、确认摘要必须经过与审计相同的脱敏与限长；事件内容不写入日志。
- **FR-010**：核心循环只通过事件契约向入口输出过程，不感知入口类型；后续新增事件存储、断线重放、SSE、AG-UI 翻译时，只增加消费方，不改核心循环与工具治理代码。

**截断与过滤**

- **FR-011**：模型调用结束原因为"达到输出上限"或"内容过滤"时，无论同步还是流式调用，本轮不再执行该次响应中的工具调用，不再发起后续模型调用，以对应错误码失败结束。
- **FR-012**：截断或过滤结束的轮次进入后续上下文时，与其他失败轮次一样只保留用户消息和一条固定的未完成说明，说明能区分"输出被截断"和"内容被过滤"。
- **FR-013**：截断或过滤不触发 Provider 重试或换模型。

**CLI 消费方**

- **FR-014**：交互式 `chat` 默认使用流式模型调用，边到达边显示文字；工具开始 / 结束各显示一行，参数摘要和结果摘要在 CLI 上进一步限长到一行内；整轮结束时不重复打印回答正文；非成功结束，或成功但本轮调用过工具时，显示一行终态（状态、模型调用次数、工具调用次数、总耗时）。
- **FR-015**：`chat --message` 保持现有输出契约：标准输出只有最终回答，失败信息与退出码与现在一致；工具进度与终态行写到标准错误。
- **FR-016**：CLI 显示的确认提示与提问沿用 006 的输入 broker，不因事件流而重复显示；事件流与提示共用同一个终端输出时不得交错打乱一行内容。
- **FR-017**：输出不是终端（被重定向或管道）时，CLI 不输出光标控制序列。

**取消**

- **FR-018**：交互式 chat 中，有轮次在执行时按 Ctrl+C 只取消当前轮次；没有轮次在执行时保持现有行为。取消后 CLI 回到输入提示，可继续对话。
- **FR-019**：取消被接受后，本轮不再发起新的模型调用、工具调用或确认请求；正在进行的模型请求和只读工具被中止；正在等待的确认按未授权处理；正在执行的有副作用工具按现有"结果未确认"规则记录，并在终态中提示"该操作可能已生效"。
- **FR-020**：用户主动取消的轮次以新的"已取消"状态持久化，与进程关闭导致的"中断"区分；取消与完成竞态时只保留先确认的终态，存储与事件一致。
- **FR-021**：取消能力经核心层的轮次控制入口提供，不依赖 CLI；后续网页端的停止按钮复用同一入口。

### Key Entities

- **运行事件（Run Event）**：一轮内发生的一件事。字段：契约版本、会话标识、轮次标识、序号、类型、产生时间、数据。会话标识与轮次标识对应后续 AG-UI 的 thread 与 run。
- **消息**：一次模型调用产生的助手文字，由消息标识关联开始、增量、结束。
- **工具调用记录**：由工具调用标识关联开始、确认、结束；与现有工具审计记录一一对应。
- **轮次终态**：完成、失败（带错误码）、取消三类之一；与持久化的轮次状态一致。新增持久化状态"已取消"。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：交互式 chat 中，模型第一段文字到达后 1 秒内显示在终端（桩模型可控延迟下测量）。
- **SC-002**：覆盖成功、工具失败、确认被拒、无人值守拒绝、超时、迭代上限、工具次数超限、截断、过滤、取消共 10 类场景，每个场景的事件序列都满足：首条为轮次开始、终态唯一且在最后、序号从 1 连续无重复无空洞。
- **SC-003**：截断与过滤样本 100% 以非成功状态结束；其中工具调用的真实执行次数为 0；下一轮上下文中截断文字出现次数为 0。
- **SC-004**：含工具调用的样本中，每个实际执行的工具都有且只有一对开始 / 结束事件，CLI 显示顺序与执行顺序一致。
- **SC-005**：取消在模型输出中、只读工具执行中、等待确认中三种阶段发出后，本轮在 2 秒内结束；取消后新的模型调用与工具调用次数为 0；有副作用工具被取消时 100% 提示"可能已生效"。
- **SC-006**：`chat --message` 成功样本的标准输出与本功能之前逐字节一致；退出码不变。
- **SC-007**：事件内容的密钥泄露样本检查中，原始密钥出现次数为 0。
- **SC-008**：`mvn -B verify` 全部通过，既有质量门不放宽。

## Assumptions

- 事件只在进程内传递，不持久化、不重放；断线重放、事件表与 SSE 在后续 Web 流式接口中实现，届时由新的消费方写入事件表，序号沿用本期规则。
- 截断与过滤不新增持久化状态，按"失败"持久化，具体原因由错误码与固定说明区分；只有"已取消"新增持久化状态（需要数据库迁移）。
- 文字增量本期不做合并，按模型分片原样发出；后续持久化时可在消费方合并，不影响契约。
- 工具参数在模型调用聚合完成后一次性放入工具开始事件，本期不做参数逐段流式；推理内容事件本期不做。
- CLI 默认不展示完整工具结果，只展示一行摘要；完整结果仍在审计表中。
- 步骤内的 Provider 重试不单独产生"重试中"事件，重试次数体现在审计记录中；如后续网页端需要再追加类型。
- 取消入口本期只接 CLI 的 Ctrl+C；跨实例取消（网页请求落到非执行实例）在后续 Web 流式接口中处理。
- 本功能是对 US-2（ReAct 循环）流式能力的补全，排在 US-3 Memory 之前执行；SSE 端点不在本期，按宪章 1.1.0 随 US-5 交付。
