**Status**: Draft

## Clarifications

### Session 2026-11-08

- Q: 调用记录应该由 Provider 在每次请求后自己写出，还是交还给调用方，由调用方来写？ → A: Provider 每发出一次请求就自己写一条记录，写入一个可替换的"记录输出"（US-1 写日志，US-2 换成写数据库）；调用结果和失败错误只附带记录供查看，调用方不再写。
- Q: 默认连接 `primary` 的 key 为空时，系统应该拒绝启动，还是像其他连接一样只标记为不可用、照常启动？ → A: 默认连接必须可用，key 为空或环境变量未设置时启动失败并指出连接名和变量名；其他连接为空时只标记为不可用。
- Q: 启动时校验 Embedding，如果服务返回的是鉴权错误或欠费，而不是网络连不上，系统应该拒绝启动，还是标记为不可用、照常启动？ → A: 标记为不可用并告警（写明鉴权失败还是欠费），照常启动；只有维度不一致才拒绝启动。
- Q: 输出上限要不要按连接类型使用不同的参数（OpenAI 兼容用 `max_completion_tokens`，DeepSeek 用真正生效的 `max_tokens`）？ → A: 要，按连接类型映射；用户补充原则：Provider 对不同模型的行为应该保持一致，同一个 Profile 参数在任何连接类型上效果相同。
- Q: 中转接口不认输出上限，这种"服务端忽略参数"的情况要怎么处理？ → A: Provider 只保证请求字段按协议发对（替身测试验证）；实际输出超过上限时打告警，并在调用记录上标记"上限未生效"；真实模型测试中 `primary` 不检查是否在上限处结束（注明中转接口的已知限制），`deepseek` 照常检查。

## User Scenarios & Testing *(mandatory)*

本 user story 的"用户"是 AgentOS 运行时内部的调用方（US-2 的 ReAct 循环，以及后续的评估器等辅助调用），不是终端用户。阶段 Demo 1 在 US-2 完成后与本 story 一起演示。

### User Story 1 - 按名称调用已配置的模型 (Priority: P1)

调用方给出 Profile（provider 名称、聊天模型、生成参数）、对话消息和可选的工具定义，系统按名称选出对应连接，组装请求并调用一次模型，返回文本、工具调用请求、结束原因和调用元数据。调用方不需要知道背后是哪家厂商。

**Why this priority**: 所有 Agent 能力都建立在"可靠地调用一次模型"之上；按名称显式路由是多 Provider 并存的前提。只完成这一条，US-2 就可以开始开发。

**Independent Test**: 配置两个同协议、指向不同本地 HTTP 替身的连接，分别按名称调用，检查每次请求只到达对应的替身，且请求内容符合 Profile。

**Acceptance Scenarios**:

1. **Given** 配置了 `primary` 和 `internal` 两个同协议连接，**When** 调用方以 `primary` 调用，**Then** 请求只到达 `primary` 的地址，`internal` 收不到任何请求。
2. **Given** Profile 指定了模型、推理强度、输出上限且没有设置温度，**When** 发起调用，**Then** 请求中携带该模型、推理强度和输出上限，且不包含温度字段。
3. **Given** 请求附带工具定义且模型返回了工具调用请求，**When** 调用完成，**Then** 结果原样包含每个工具调用的 ID、名称、参数和顺序，系统没有执行任何工具。
4. **Given** Profile 指定的 provider 名称不存在，或没有指定聊天模型，**When** 发起调用，**Then** 调用在发出任何网络请求之前失败，错误指明缺的是什么，系统不会改用其他连接或模型。
5. **Given** 测试环境的 `primary` 已配置真实凭证，**When** 运行单独开启的冒烟测试，**Then** 同步调用返回非空结果，调用记录中的实际模型和 token 用量有值。
6. **Given** 默认连接 `primary` 的凭证为空、可选连接 `deepseek` 的凭证也为空，**When** 系统启动，**Then** 启动失败并指出 `primary` 缺少的环境变量；只把 `primary` 补上后，启动成功，`deepseek` 标记为不可用。

### User Story 2 - 失败时有限重试，并在截止时间内结束 (Priority: P2)

模型服务出错时，系统区分"可能是暂时故障"和"重试也没用的错误"：前者最多追加一次重试，后者立即失败；任何情况下调用都不能拖过本轮剩余时间。最终失败以统一的 Provider 故障报给调用方。

**Why this priority**: 第三方中转、限流和网络抖动在测试环境都会出现。没有这一条，ReAct 循环会被一次慢调用拖垮整轮预算，或者对鉴权错误反复重试。

**Independent Test**: 让 HTTP 替身按脚本依次返回 429、503、401 等响应，统计实际请求次数、等待时间和最终错误类型。

**Acceptance Scenarios**:

1. **Given** 替身第一次返回 429 并带 `Retry-After: 1`，第二次返回成功，**When** 发起调用，**Then** 共发出 2 次请求，两次间隔不少于 1 秒，调用方拿到成功结果。
2. **Given** 替身连续两次返回 503，**When** 发起调用，**Then** 共发出 2 次请求，调用方收到 Provider 故障（`PROVIDER_UNAVAILABLE`）。
3. **Given** 替身返回 401 或 400，**When** 发起调用，**Then** 只发出 1 次请求，立即失败，不重试。
4. **Given** 本轮剩余时间不足以完成一次完整的重试（或 `Retry-After` 超过剩余时间），**When** 首次请求遇到可重试错误，**Then** 不再重试，直接以 Provider 故障结束。
5. **Given** 连接超时为 120 秒、本轮只剩 30 秒，替身一直不响应，**When** 发起调用，**Then** 调用在 30 秒左右以超时失败，而不是等满 120 秒。

### User Story 3 - 每次请求都留下可追溯的调用记录 (Priority: P2)

每一次实际发往模型服务的请求（包括重试和失败）都产生一条调用记录，内容足以回答"这次用了哪个连接、请求和实际的模型是什么、成功没有、用了多少 token、限流余量多少、为什么结束、花了多久"。拿不到的数据记为空，不能伪装成 0。记录里不包含凭证、完整 Prompt 和工具参数。本 story 写入结构化日志，审计表落库在 US-2 完成。

**Why this priority**: 可审计是 AgentOS 的差异化能力（宪章原则六）。现在把采集口径定准，US-2 只需要把同一份记录写进数据库。

**Independent Test**: 用替身返回带完整用量、缺少用量、缺少限流头等不同响应，检查日志中的调用记录字段和条数。

**Acceptance Scenarios**:

1. **Given** 一次调用先 429 后成功，**When** 调用结束，**Then** 日志中有 2 条调用记录：第 1 条失败并带脱敏错误，第 2 条成功并带用量。
2. **Given** 替身响应里没有缓存 token 字段、没有限流响应头，**When** 调用结束，**Then** 记录中缓存 token 和限流余量为空，而不是 0。
3. **Given** 替身响应里带有缓存命中的 token 数，**When** 调用结束，**Then** 记录中的缓存读取 token 等于该数值。
4. **Given** 请求包含 API key、完整对话和工具参数，**When** 检查本次调用产生的全部日志，**Then** 找不到 API key 原文、完整 Prompt 和工具参数。
5. **Given** 调用方传入了会话、轮次、迭代标识，**When** 调用结束，**Then** 记录带上这些标识；调用方没有传时这些字段为空。

### User Story 4 - 流式调用 (Priority: P3)

调用方可以选择流式调用：文本增量到达时可以转交给调用方的输出端；调用结束后，系统仍交出一份与同步调用等价的完整结果（文本、工具调用请求、结束原因、用量）。工具调用的名称和参数可能分散在多个分片里，必须拼完整后才交出。

**Why this priority**: 阶段 Demo 1 用同步调用就能完成；流式能改善交互体验，也是扩展阶段 SSE 的基础，接口要现在定好。

**Independent Test**: 让替身以分片方式返回文本和一个参数被拆开的工具调用，比对聚合结果与同步调用结果，并检查输出端收到的增量顺序。

**Acceptance Scenarios**:

1. **Given** 替身把一个工具调用的参数拆成 3 个分片发送，**When** 流式调用结束，**Then** 结果中该工具调用的参数完整，且系统没有执行该工具。
2. **Given** 流在中途断开，且已经有文本增量交给了输出端，**When** 调用结束，**Then** 调用以失败结束并留下失败记录，系统不自动重发这次请求。
3. **Given** 流在还没有交出任何增量时遇到可重试错误，**When** 首次请求失败，**Then** 按 User Story 2 的规则最多重试 1 次。
4. **Given** 一次正常的流式调用，**When** 调用结束，**Then** 只产生 1 条调用记录，用量没有被重复累加。

### User Story 5 - 文本向量化 (Priority: P3)

调用方提交一段或一批文本，系统用全局唯一的向量化模型返回对应的向量，维度与配置一致。向量化与聊天连接分开配置：换聊天模型不影响向量，反过来也一样。

**Why this priority**: US-3 的记忆检索和后续知识库都依赖向量化，在 US-1 把它和聊天连接一起定好，下游直接使用。向量存储（向量表、检索）不在本 story 范围内。

**Independent Test**: 用替身模拟向量化服务，检查请求地址、模型、维度参数、分批次数和结果顺序；单独开启的冒烟测试调用真实服务。

**Acceptance Scenarios**:

1. **Given** 配置的维度为 1024，**When** 向量化一段文本，**Then** 返回 1 个 1024 维的向量，请求中显式携带维度。
2. **Given** 单次请求上限为 10 条，**When** 一次提交 11 条文本，**Then** 系统分 2 次请求发送，返回 11 个向量，顺序与输入一致。
3. **Given** 向量化未启用或凭证为空，**When** 系统启动，**Then** 不创建向量化组件，启动不受影响；调用方请求向量化时得到"未启用"的明确错误。
4. **Given** 服务返回的向量维度与配置不一致，**When** 系统启动时校验，**Then** 拒绝启动，并指出配置值和实际值。
5. **Given** 校验请求返回鉴权失败或欠费，**When** 系统启动，**Then** 启动成功，向量化标记为不可用，告警日志写明是鉴权失败还是欠费；之后请求向量化得到"不可用"的明确错误。
6. **Given** 测试环境已配置向量化凭证，**When** 运行单独开启的冒烟测试，**Then** 返回 1024 维向量。

### Edge Cases

- 两个连接使用同一协议、同一种实现：只能按名称区分，不能根据类型或注册顺序推断。
- 某个连接的凭证环境变量为空（例如可选的 `deepseek`）：该连接标记为不可用，不影响其他连接；以它的名称调用时在外呼前失败。
- 配置了本 story 不支持的连接类型（如 `anthropic`、`ollama`）：启动失败，错误指明连接名称和不支持的类型，不能当作 OpenAI 兼容类型处理。
- Profile 没写 provider 名称：使用全局默认 provider。默认 provider 未配置或凭证为空时，系统在启动阶段就失败（FR-003），不会等到调用时。
- 模型只返回工具调用、没有文本：视为有效响应。
- 响应中没有任何候选结果：按协议异常处理，调用失败，不重试。
- 模型拒答或达到输出上限：不是错误，结束原因原样交给调用方，由调用方决定怎么处理。
- 调用方没有提供工具清单：请求中不带任何工具定义，不能回退到某个默认工具集。
- 调用方随请求带的应用侧上下文（会话、权限等）：不能出现在发给模型服务的请求内容里。
- 调用方取消调用：立即停止等待，记录为失败，不重试。
- 向量化提交空列表：直接返回空结果，不发请求。
- 单条文本超过向量化服务的长度上限：把服务的错误交给调用方，不擅自截断。
- 启动时向量化服务不可达、key 错误或账号欠费：标记为不可用，告警写明原因，不阻断启动；本次运行期间保持不可用，重启后重新校验。只有维度不一致才拒绝启动。

## Requirements *(mandatory)*

### Functional Requirements

**连接配置**

- **FR-001**: 系统 MUST 支持在全局配置中声明多个具名连接，每个连接包含：唯一名称、类型、服务地址、API key、超时。连接配置 MUST NOT 包含聊天模型。
- **FR-002**: API key MUST 以环境变量占位的方式配置，启动时解析；仓库、配置文件和日志中 MUST NOT 出现明文凭证。
- **FR-003**: 系统 MUST 在启动时校验连接配置：名称唯一、类型受支持、超时为正数，违反时 MUST 启动失败。默认连接（`default-provider` 指向的连接）MUST 存在且凭证非空，否则 MUST 启动失败，错误指明连接名称和缺少的环境变量；其他连接凭证为空时 MUST 标记为不可用，不阻断启动。
- **FR-004**: 系统 MUST 维护"连接名称 → 连接"的显式映射，MUST NOT 根据实现类型或注册顺序推断连接。
- **FR-005**: 本 story 支持两种连接类型：OpenAI 兼容（`openai`，DeepSeek、Kimi、通义兼容模式、内部中转都可以用它接入）和 DeepSeek 专用（`deepseek`）。配置中出现其他类型（如 `anthropic`、`ollama`）时 MUST 启动失败，并提示该类型暂不支持；`type` 字段保留，后续增加类型不改变配置格式。两种类型 MUST 都通过本地 HTTP 替身的协议测试，并各有一个可单独开启的真实模型冒烟测试。

**Profile 契约与请求组装**

- **FR-006**: 系统 MUST 定义 Profile 契约，至少包含：provider 名称（可选，缺省时用全局默认 provider）、聊天模型（必填）、推理强度（可选）、输出上限（可选）、温度（可选）。从 AGENT.md 派生 Profile 不在本 story 范围内。
- **FR-007**: provider 名称未知、对应连接不可用、或 Profile 缺少聊天模型时，系统 MUST 在发出网络请求之前失败，错误 MUST 指明原因；MUST NOT 静默改用其他连接或模型。
- **FR-008**: 请求中的生成参数 MUST 只来自本次 Profile：Profile 没有设置的参数（包括温度）MUST NOT 出现在请求中，不得用默认值补齐。
- **FR-009**: Profile 中每个生成参数（推理强度、输出上限、温度）的语义 MUST 在所有连接类型上保持一致：同一个 Profile 换一个连接类型，可观察的效果相同。各连接类型 MUST 把参数映射成该服务真正生效的请求字段，每个参数只发送一个字段。输出上限的映射：`openai` 发送"最大完成 token"字段，`deepseek` 发送"最大 token"字段（实测 DeepSeek 会忽略"最大完成 token"）。某种连接类型无法生效的参数 MUST 在外呼前失败，MUST NOT 静默忽略。服务端忽略了已按协议正确发送的参数，不属于外呼前能拦住的情况：Profile 设置了输出上限、而实际输出 token 超过上限时，MUST 打告警，并在调用记录中标记"上限未生效"。
- **FR-010**: 每次请求的工具清单 MUST 完全由调用方提供；调用方未提供时请求中 MUST NOT 带工具定义。
- **FR-011**: 调用方随请求携带的应用侧上下文 MUST NOT 出现在发给模型服务的请求内容中。
- **FR-012**: 单次请求的超时 MUST 取"连接超时"与"本轮剩余时间"中较小的值。

**调用与结果**

- **FR-013**: 系统 MUST 支持同步调用，返回完整结果：文本、按顺序排列的工具调用请求（ID、名称、参数）、结束原因、调用元数据。
- **FR-014**: 系统 MUST 支持流式调用：文本增量可以交给调用方的输出端；调用结束后 MUST 交出与同步调用等价的完整结果，跨分片的工具调用 MUST 拼接完整后才交出。
- **FR-015**: 系统 MUST NOT 执行任何工具，也 MUST NOT 自行发起下一次模型调用；循环和工具执行由调用方负责。
- **FR-016**: 只有工具调用、没有文本的响应 MUST 视为有效结果；没有任何候选结果的响应 MUST 视为调用失败。

**重试与失败**

- **FR-017**: 只有以下失败可以重试：429、可重试的 5xx、临时连接错误（含读超时）。每次调用最多追加 1 次重试。
- **FR-018**: 重试前 MUST 确认本轮剩余时间足以完成一次完整请求；有 `Retry-After` 时 MUST 等待其指定的时间，等待时间也计入本轮时间，超出剩余时间则不重试。
- **FR-019**: 流式调用已向输出端交出增量后，MUST NOT 重试。
- **FR-020**: 鉴权错误、参数错误、未知模型、配置错误、调用方取消 MUST 立即失败，不重试。
- **FR-021**: 最终失败 MUST 以 Provider 故障（错误码 `PROVIDER_UNAVAILABLE`）交给调用方，错误信息 MUST 脱敏；外呼前的校验失败（FR-007）使用参数错误类错误码。

**调用记录**

- **FR-022**: 每一次实际发出的请求（含重试、含失败）MUST 产生一条调用记录，字段见 Key Entities 中的"调用记录"。记录 MUST 由 Provider 在该次请求结束时写入"记录输出"，不依赖调用方；所有尝试都失败时，每次尝试的记录也 MUST 已经写出。外呼前就失败（FR-007）的调用没有实际请求，不产生记录。
- **FR-023**: 模型服务没有提供的用量、缓存 token、限流余量 MUST 记为空；MUST NOT 记为 0。模型服务明确返回 0 时记为 0。
- **FR-024**: 调用记录和日志 MUST NOT 包含凭证、完整 Prompt、工具参数和原始响应体；错误信息 MUST 脱敏后再写入。
- **FR-025**: "记录输出" MUST 可替换：本 story 的实现写入结构化日志，并在代码中标注 TODO 指向 US-2 的 `llm_calls` 表落库；US-2 替换输出时 MUST NOT 修改 Provider 的调用逻辑。调用结果和失败错误 MUST 附带本次调用的全部记录，供调用方查看，调用方不再写记录。
- **FR-026**: 模型调用 MUST 接入运行时的统一观测，便于统计调用次数和耗时；观测内容 MUST NOT 包含 Prompt、工具参数和凭证。

**验证**

- **FR-027**: MUST 提供离线协议测试：用本地 HTTP 替身验证最终请求地址（包括聊天和向量化的地址是否需要带 `/v1`）、请求内容（不含温度）、实际请求次数、工具未被执行。
- **FR-028**: MUST 提供可单独开启的真实模型冒烟测试（聊天与向量化），没有凭证时自动跳过，不在默认构建中运行。

**向量化（Embedding）**

- **FR-029**: 系统 MUST 支持单独配置一个向量化连接：服务地址、API key（环境变量占位）、模型、维度、单次请求条数上限、超时、是否启用。向量化的模型和维度是全局配置，不由 Agent 的 Profile 决定，也不和任何聊天连接绑定。
- **FR-030**: 系统中 MUST 只存在一个向量化模型实例；MUST NOT 因为聊天连接或其他自动配置，额外生成一个指向聊天端点的向量化实例。
- **FR-031**: 未启用或凭证为空时，MUST NOT 创建向量化组件，且不影响启动；此时请求向量化 MUST 得到明确的"未启用"错误。
- **FR-032**: 每次向量化请求 MUST 显式携带配置的维度。启用时 MUST 在启动阶段用一次实际向量化的结果长度与配置比对，不一致 MUST 拒绝启动。校验请求因服务不可达、鉴权失败或欠费而失败时，MUST 把向量化标记为不可用、不阻断启动，并打告警日志写明失败类别（不可达 / 鉴权失败 / 欠费）。
- **FR-033**: 一次提交的文本数超过单次上限时，系统 MUST 自动分批发送，返回的向量数量和顺序 MUST 与输入一致。
- **FR-034**: 向量化的重试规则与聊天调用一致（FR-017、FR-020）：只对 429、可重试的 5xx、临时连接错误追加 1 次；模型库自带的重试 MUST 关闭。
- **FR-035**: 向量化调用 MUST 记录结构化日志（模型、文本条数、请求次数、token 用量、成功与否、耗时）；日志和观测 MUST NOT 包含原文、向量值和凭证。

### Key Entities

- **Provider 连接**：一个具名的模型服务端点。属性：名称、类型、服务地址、凭证引用、超时、是否可用。启动时建立，运行期间不变。
- **Profile**：一个 Agent 调用模型时的选择与参数。属性：provider 名称、聊天模型、推理强度、输出上限、温度。本 story 只定义契约，由调用方直接构造。
- **调用请求**：一次调用的输入。包含 Profile、对话消息、工具定义、应用侧上下文、本轮截止时间、调用方式（同步 / 流式）。
- **调用结果**：一次调用的输出。包含文本、工具调用请求列表、结束原因、本次调用的全部记录（只读，已由 Provider 写出）。失败时，Provider 故障错误同样附带全部记录。
- **记录输出**：调用记录的写入目标，可替换。US-1 为结构化日志，US-2 为 `llm_calls` 表。
- **向量化配置**：全局唯一的向量化服务连接。属性：服务地址、凭证引用、模型、维度、单次条数上限、超时、是否启用、是否可用。
- **调用记录**：一次实际请求的审计信息，对应 US-2 的 `llm_calls` 表。字段：会话 / 轮次 / 迭代标识（调用方提供，可为空）、provider 名称、请求模型、响应 ID、实际模型、调用方式、第几次尝试、结束原因、工具调用数、输入 / 输出 / 总 token、缓存读取 / 写入 token、剩余请求数 / 剩余 token 数、输出上限是否生效（只在 Profile 设置了上限时有值）、是否成功、脱敏错误、耗时。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 两个同协议连接并存时，按名称调用的路由正确率为 100%，没有任何请求到达错误的端点。
- **SC-002**: 未知 provider、不可用连接或缺少聊天模型的调用，发出的网络请求数为 0。
- **SC-003**: 可重试失败的单次调用最多发出 2 次请求；不可重试失败只发出 1 次。
- **SC-004**: 任何一次调用的总耗时不超过本轮剩余时间加 1 秒的容差。
- **SC-005**: 调用记录条数与实际请求次数一一对应，覆盖率 100%。
- **SC-006**: 模型服务没有提供的用量和限流数据，被记为 0 的次数为 0。
- **SC-007**: 在全部测试产生的日志中，API key 原文、完整 Prompt、工具参数出现次数为 0。
- **SC-008**: Profile 未设置温度时，请求中出现温度字段的次数为 0。
- **SC-009**: 工具被系统执行的次数为 0。
- **SC-010**: 真实模型冒烟测试中，同步和流式调用都返回有效结果，模型返回的工具调用请求被完整交出。
- **SC-011**: `openai` 与 `deepseek` 两种连接类型的离线协议测试通过率 100%；配置不支持的类型时启动失败率 100%。
- **SC-012**: 返回向量的维度与配置一致的比例为 100%；维度不一致时启动失败率 100%。
- **SC-013**: 提交 N 条文本时，请求次数等于 N 除以单次上限后向上取整，返回 N 个向量且顺序与输入一致。
- **SC-014**: 向量化未启用时，系统中向量化实例数为 0，启动不受影响。
- **SC-015**: 设置了输出上限的 Profile，离线协议测试中 `openai` 与 `deepseek` 各自只发送该类型生效的那一个字段，正确率 100%；通过 `deepseek` 调用真实模型时，结束原因为"达到输出上限"且输出 token 数不超过上限。
- **SC-016**: 实际输出 token 超过 Profile 输出上限的调用，被标记"上限未生效"并产生告警的比例为 100%。

## Assumptions

- 调用方是 US-2 的 ReAct 循环和后续的辅助调用；本 story 没有面向终端用户的入口，阶段 Demo 1 在 US-2 完成后一起演示。
- 从 AGENT.md 派生 Profile、`llm_calls` 落库属于 US-2；向量存储（向量表、pgvector 扩展、检索）属于 US-3；fallback、hedge racing、熔断属于扩展阶段；`anthropic`、`ollama` 连接类型在有实际需求和凭证时再加。
- DeepSeek 测试凭证已提供（2026-11-08 实测）：账号可用模型为 `deepseek-flash`、`deepseek-v4-pro`；`deepseek-flash` 支持工具调用，响应带推理 token；用量中缓存 token 明确返回 0（按 FR-023 记为 0，不是空）；没有限流响应头（限流余量记为空）；推理强度 `low` / `high` 生效，非法值返回 422；`max_completion_tokens` 不报错但被忽略，`max_tokens` 生效（结束原因为 `length`）。
- 可重试的 5xx 指 500、502、503、504；其他 5xx（如 501）不重试。调用方没有传本轮截止时间时，单次请求只受连接超时约束。
- `primary` 与 `deepseek` 是同级的两个供应商连接，配置结构一致（类型、地址、凭证、超时），变量统一用 `AGENTOS_<供应商>_*` 命名；Agent 在 Profile 里按名称选用。评估测试选哪个模型属于验收阶段（技术方案 12.4）的决定，不是 Provider 的属性。
- 百炼向量化已用新测试凭证实测（2026-11-08）：`text-embedding-v4` 返回 1024 维；单次 10 条成功、11 条返回 400；请求路径必须是 `<base-url>/v1/embeddings`，不带 `/v1` 返回 404。
- 向量化调用不写 `llm_calls` 表（该表只记录聊天调用），只写结构化日志。
- Profile 没有设置推理强度或输出上限时，请求不带这两个参数，由模型服务使用自己的默认值。
- 本轮截止时间由调用方传入；本 story 的测试直接构造。
- 没有 `Retry-After` 时，重试前使用 1 秒以内的短暂等待，具体数值在 plan 中确定。
- 测试环境的中转接口已实测（2026-11-08）支持同步与流式工具调用、流式用量（含缓存命中 token）和结构化输出。
- 测试环境的中转接口不遵守任何输出上限字段（实测 `max_completion_tokens`、`max_tokens`、`max_output_tokens` 设为 20 时，实际输出 62 ~ 90 token，结束原因 `stop`）。这是中转服务的已知限制；US-2 控制花费主要依靠最大迭代次数和整轮超时。
- base URL 是否需要带 `/v1` 在实现时由替身测试确定；结论与技术方案 3.5 节、`.env` 不一致时，同步修正两者。
- 本描述中"聊天模型只由 Profile 提供"与技术方案 3.2 节不同，以本描述为准；US-1 完成后同步修订技术方案。
- 自动化测试不连共享数据库，也不调用真实模型；真实模型冒烟按宪章「技术约束」用标签和环境变量开启。
